2. 主 agent 用 `fromelf -z` 逐个统计 `.lnp` 里链接的 21 个 `.o`，定位真正根因：**`protocol_codec.o` 单独 code = 112,640 B**（其余 20 个合计约 14.5 KB）。原因是 `Protocol_Crc16` 运行时直接展开 8 层嵌套的 `CRC_STEP` 宏，`CRC_BIT1(c)` 的三元式让 `(c)` 每层出现 3 次 → 3^8 份表达式。证据：`outputs/keil_probe/P3链接溢出根因.txt`。
3. 修复：`Protocol_Crc16` 改为循环调用**同一个 `CRC_BIT1` 单步宏** 8 次；编译期 `#if` 断言仍用 `CRC_STEP`（预处理期求值、不生成代码），两者语义由同一宏保证。实测修复后该 `.o` code = **264 B**，`docs/protocol.md` 第 5 节参考实现已同步修正并注明该坑。
4. 随后 `UV4 -r` 全量重建成功，HEX 生成。

**最终复核（15:44）**：主 agent 统一了 3 处源码注释措辞（仅注释，不改任何代码、宏定义或工程配置）后，再次执行 `UV4 -r` 全量重建，仍为 `ExitCode 0 / 0 Error(s), 0 Warning(s)`，`Program Size` 完全一致，HEX 重新生成（45,485 B，15:44:58）。结论稳定、可复现。

## 7. 未验证项清单（固定部分，不随整合变化）

1. **未接线 / 未烧录 / 未上电**：本机没有接入开发板，也没有自动烧录。见 `docs/上板验收.md`。

3. **未测精度与带宽**：未用已知电压源校准，未测 ADC 线性度、噪声、有效位数；100 kS/s 是设计目标。

5. **未测晶振与电源**：8MHz HSE / 72MHz SYSCLK / 3.3V 均来自参考工程配置，实际板子需现场确认。
6. **未做运行级 C↔Python 双向核对**：本机没有可在 PC 上执行的 x86 C 编译器（已查 `gcc` / `cc` / `clang` / `cl.exe` 均不可用，`.NET csc.exe` 编译被环境安全策略拦截），因此固件 C 函数无法编译成 PC 程序执行；现有跨实现证据是 ARMCC 编译期 `#if` 常量断言 + Python 独立解析 C 源码中的人工 golden 字节。若后续有 GCC/MSVC，应补做「C 编码→Python 解码」与「Python 编码→C 解码」。
7. **未做长时间稳定性实测**：连续运行数小时的内存/线程/串口稳定性未验证（代码里设了缓冲区上限与释放逻辑）。
