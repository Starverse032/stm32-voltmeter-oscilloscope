# STM32 电压表 / 示波器 通信协议 v1

> 本文件由主 agent 统一制定，是固件与电脑端**唯一**的接口依据。
> 两端任何一方需要改字段，必须先改本文件并通知另一端，不允许各自扩展私有格式。
> 版本 1，日期 2026-11-09。本文中的"必须 / 不得"是硬性约束。

---

## 1. 物理层与字节序

| 项目 | 规定 |
| --- | --- |
| 链路 | USART1，PA9 = TX（设备→电脑）、PA10 = RX（电脑→设备） |
| 参数 | 115200 baud，8 数据位，无校验，1 停止位（8N1），无流控 |
| 电平 | TTL UART；USB 转 TTL 模块必须是 3.3V 逻辑电平；必须共地 |
| 字节序 | **所有多字节整数一律小端（Little Endian）**，与 Cortex-M3 / STM32F103 原生一致；Python 侧用 `struct` 的 `<` 前缀 |
| 编码 | 二进制帧。**禁止**把调试 `printf`、日志、文本提示写进该串口；调试输出只能走别的通道或彻底关闭 |
| 方向 | 电脑→设备：命令帧（0x20）；设备→电脑：采样帧（0x10）、响应帧（0x21）、事件帧（0x22） |
| 连续传输能力 | 115200 8N1 理论上限约 11520 B/s。一帧 1024 点 = 2070 字节 ≈ 180 ms。**只做"采集一帧 → 停止采样 → 发送一帧"**，帧间存在空隙，本协议不声称连续无损 100 kS/s 实时流 |

## 2. 通用帧结构

```
偏移    长度   字段        说明
0       4     MAGIC       固定 A5 5A C3 3C（用于噪声后重同步）
4       1     VER         协议版本 = 0x01；不是 0x01 的帧必须丢弃并上报版本不匹配
5       1     TYPE        帧类型，见第 3 节
6       2     LEN         payload 字节数，uint16 LE，取值 0..2060
8       1     SEQ         序号，见第 3 节
9       1     FLAGS       保留，必须 = 0x00；收到非零值不视为错误，忽略即可
10      LEN   PAYLOAD     按 TYPE 解释，见第 4 节
10+LEN  2     CRC16       uint16 LE，见第 5 节
```

- **固定头 = 10 字节，尾 = 2 字节，整帧长度 = LEN + 12。**
- `LEN_MAX = 2060`（= 10 字节采样元信息 + 2×1024 字节样本）。**整帧合法长度上限 = 2072 字节**。
- 接收端缓冲区硬上限 `RX_BUF_MAX = 8192` 字节。超过即整体清空并重新寻找 MAGIC，防止长时间运行内存增长与恶意长度导致的死等。
- `LEN` 与 `TYPE` 必须自洽（见 4.1），不自洽的帧按 CRC 错误处理，不得按 `LEN` 硬读后当作有效帧。

### 2.1 SEQ 语义

| 帧类型 | SEQ 来源 | 用途 |
| --- | --- | --- |
| 命令帧 0x20 | 电脑生成，逐命令 +1（0..255 回绕） | 匹配响应 |
| 响应帧 0x21 | **必须原样回显对应命令的 SEQ** | 电脑据此判断"这条命令是否被设备确认" |
| 采样帧 0x10 | 设备自己维护的帧计数低 8 位，每成功发出一帧 +1 | 电脑检测丢帧、CSV 记录帧号 |
| 事件帧 0x22 | 设备自增，与命令 SEQ 无关 | 仅用于显示/日志 |

**关键约束**：采样率切换、参考电压修改、启动/停止/单次命令，**只有收到 SEQ 匹配、status=0x00 且参数回读正确的响应帧才算生效**。仅发出命令、或收到不匹配 SEQ 的响应，都必须保持旧状态并提示用户，不得静默当作成功。

## 3. 帧类型

| TYPE | 名称 | 方向 | 允许 LEN |
| --- | --- | --- | --- |
| `0x10` | SAMPLE 采样帧 | 设备 → 电脑 | `10 + 2*N`，N = 1..1024 |
| `0x20` | COMMAND 命令帧 | 电脑 → 设备 | 1..8 |
| `0x21` | RESPONSE 响应帧 | 设备 → 电脑 | 固定 14 |
| `0x22` | EVENT 事件/错误帧 | 设备 → 电脑 | 1..64 |

未知 TYPE：整帧丢弃，计数一次协议错误，不尝试解释 payload。

> 第一版固件**固定每帧 1024 点**；但解析器**必须**支持 1..1024 点，以便用短帧做协议测试与后续扩展。短采样帧是合法的协议帧，不是错误。

## 4. Payload 定义

### 4.1 SAMPLE（TYPE = 0x10）

```
偏移  长度  字段              类型        说明
0     4    sample_rate_hz     uint32 LE  **真实生效的采样率**，如 10000 / 100000。不得由电脑猜测
4     2    point_count        uint16 LE  样本点数 N，必须 = (LEN-10)/2，且 1..1024
6     2    vref_mv            uint16 LE  设备当前采用的参考电压，单位 mV（如 3300）
8     2    reserved           uint16 LE  必须为 0
10    2*N  samples[i]         uint16 LE  12 位 ADC 右对齐原始码，0..4095；高位必须为 0
```

约束：
- `sample_rate_hz` 与 `point_count` 必须满足 `LEN == 10 + 2*point_count`，否则丢弃。
- 样本值 > 4095 时视为数据损坏，整帧丢弃（不得截断后照常显示）。
- v1 的 `sample_rate_hz` 只允许 10000/100000，`vref_mv` 只允许 2500..3600；非法元信息整帧丢弃，不进入绘图或导出。
- 电压换算：`V = code / 4095.0 * (vref_mv / 1000.0)`。**设备 OLED 与电脑端必须使用同一个 `vref_mv`**，电脑端不得自行假定 3.300 V。
- `vref_mv` 是可配置量，**掉电不保存**（第一版只改 RAM），设备复位后回到编译默认值。电脑端必须显示"设备参考电压"，并注明是否同步、是否掉电保存。
- 时间轴：`t_i = i / sample_rate_hz`（秒），**每帧从 0 重新开始**。帧间空隙不隐藏：CSV 记录 `frame_seq` 且文件头注明"帧间不连续，时间轴为帧内相对时间"。

### 4.2 COMMAND（TYPE = 0x20）

`payload[0] = cmd_id`，其后为参数（无参数时 LEN = 1）。

| cmd_id | 名称 | 参数 | 设备行为 |
| --- | --- | --- | --- |
| `0x01` | START | 无 | 进入连续采集：反复"采一帧→停→发一帧" |
| `0x02` | STOP | 无 | 停止采样；当前帧发完后不再启动新帧 |
| `0x03` | SINGLE | 无 | 只采集并发送 **1** 帧，完成后回到 IDLE |
| `0x04` | SET_RATE | 4 字节 uint32 Hz | 只允许 `10000` 或 `100000`；其他值回 `0x01` 参数非法 |
| `0x05` | SET_VREF | 2 字节 uint16 mV | 允许 `2500..3600`；其他值回 `0x01` |
| `0x06` | PING | 无 | 立即回响应，用于连接保活 |
| `0x07` | SELFTEST_PWM | 1 字节 0/1 | 开关 PA8 的 100 Hz 自检 PWM |
| `0x08` | QUERY_STATUS | 无 | 只回响应，不改变运行状态 |

- 命令参数长度不符 → 回 `status=0x01`。
- Codex 复核版：设备只在完整帧处理完后的帧间调用命令解析；采集/发送期间 RX 中断继续缓存字节。SINGLE 响应在该次新采样之前发出，电脑收到匹配 SEQ/status/run_state 的确认后才接纳单次结果，丢弃此前仍在途的旧帧。
- START/STOP 也需匹配 SEQ/status/run_state，超时显示设备状态未知。过期 ACK 不得取消更新的请求。上升沿单次未触发时，电脑可以再次发送 SINGLE；每个设备 SINGLE 仍只采发一帧。
- 在 SINGLE_BUSY / 发送中收到 SET_RATE：回 `status=0x02`（忙），**不改参数**；电脑端必须提示"设备忙，未切换"。
- 设备**不得**在没有电脑连接时等待握手：上电后独立完成 ADC/OLED 初始化并按默认状态运行电压表显示；串口命令只是附加控制通道。

### 4.3 RESPONSE（TYPE = 0x21，LEN = 14）

```
偏移  长度  字段              类型        说明
0     1    ack_cmd            uint8      对应的 cmd_id；0x00 表示设备主动状态上报
1     1    status             uint8      0x00 OK / 0x01 参数非法 / 0x02 忙 / 0x03 不支持 / 0x04 硬件错误
2     4    actual_rate_hz     uint32 LE  设备**当前实际**采样率
6     2    vref_mv            uint16 LE  设备当前参考电压
8     1    run_state          uint8      0 IDLE / 1 RUN / 2 SINGLE_BUSY
9     1    dev_flags          uint8      bit0 = 自检 PWM 已开启；其余 0
10    4    frames_sent        uint32 LE  设备累计已发送采样帧数
```

`status != 0x00` 时，`actual_rate_hz` / `vref_mv` 仍必须填**设备当前的真实值**（不是请求值），电脑端据此回滚显示。

### 4.4 EVENT（TYPE = 0x22）

```
偏移 0：code（0x01 协议错误 / 0x02 ADC 溢出或 DMA 异常 / 0x03 帧被丢弃 / 0x04 帧间隔异常 / 0x05 其他）
偏移 1..：可选 ASCII 简短说明（不得出现中文，避免编码歧义），长度 ≤ 63
```

电脑端必须把 EVENT 显示到状态栏，不能静默吞掉。

## 5. CRC

- 算法：**CRC-16/CCITT-FALSE**（poly `0x1021`，初值 `0xFFFF`，输入不反射，输出不反射，xorout `0x0000`，逐字节 MSB first）。
- 标准自检向量：`crc16("123456789") == 0x29B1`。
- 覆盖范围：**从 `VER`（偏移 4）到 `PAYLOAD` 最后一个字节**，即整帧去掉前 4 字节 MAGIC 和末尾 2 字节 CRC，**共 `6 + LEN` 字节**。
- 帧内存储：CRC 的**低字节在前**（小端）。例如 CRC = `0x8278` → 字节 `78 82`。
- 不含 MAGIC 是为了让接收端在滑动搜索到 MAGIC 后能直接校验其余全部字段（版本、类型、长度、序号、标志、数据），长度被篡改也能被发现。

参考实现（C，与固件共用；`CRC_STEP` 同时用于运行时函数和编译期静态断言）：

```c
/* 纯常量表达式：既用于运行时函数体，也用于编译期 #if 静态断言 */
#define CRC_BIT1(c)  (((c) & 0x8000u) ? ((((c) << 1) ^ 0x1021u) & 0xFFFFu) : (((c) << 1) & 0xFFFFu))
#define CRC_STEP(c, b) \
    CRC_BIT1(CRC_BIT1(CRC_BIT1(CRC_BIT1(CRC_BIT1(CRC_BIT1(CRC_BIT1(CRC_BIT1((((uint16_t)(c)) ^ (((uint16_t)(b)) << 8)))))))))))

/* 运行时实现：用循环调用同一个 CRC_BIT1 单步宏 8 次。
 * 注意：运行时**不要**直接展开 8 层嵌套的 CRC_STEP —— CRC_BIT1 的三元表达式
 * 会让 (c) 每层出现 3 次，8 层嵌套 = 3^8 份表达式，ARMCC 会编译出约 110 KB
 * 机器码，直接撑爆 STM32F103C8 的 64 KB Flash（本项目实测踩过这个坑）。
 * CRC_STEP 宏专用于编译期 #if 常量断言（预处理期求值，不生成代码）。
 * 两者都由 CRC_BIT1 定义，语义完全一致。 */
uint16_t Protocol_Crc16(const uint8_t *data, uint32_t len)
{
    uint16_t crc = 0xFFFFu;
    uint32_t n;
    uint8_t bit;
    for (n = 0; n < len; n++)
    {
        crc ^= (uint16_t)((uint16_t)data[n] << 8);
        for (bit = 0; bit < 8; bit++) { crc = (uint16_t)CRC_BIT1(crc); }
    }
    return crc;
}
```

该宏展开后的语义已核对：`CRC_STEP` 迭代 8 次 `CRC_BIT1`，`Protocol_Crc16` 对 `"123456789"` 得 `0x29B1`，对第 7 节三帧的 CRC 覆盖段分别得 `0x8278` / `0x7EA4` / `0xE73A`。实测：循环版 `Protocol_Crc16` 编译后 code 仅 **58 字节**，而嵌套宏版为 **112,640 字节**（`fromelf -z`）。

参考实现（Python，与电脑端共用，`crcmod` 等第三方库不作为依赖）：

```python
def crc16_ccitt_false(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if (crc & 0x8000) else (crc << 1) & 0xFFFF
    return crc
```

## 6. 接收状态机与重同步规则（两端都要实现）

串口一次 `read()` **不等于**一个完整包；必须实现字节流解析：

1. 维护字节缓冲 `buf`，追加新收到的数据；`len(buf) > RX_BUF_MAX` 时整体清空、重新同步并上报一次错误。
2. 在 `buf` 中搜索 4 字节 MAGIC `A5 5A C3 3C`；未找到时只保留末尾 3 字节（防止 MAGIC 被分片切断），丢弃其余噪声字节。
3. 找到 MAGIC 后，若 `buf` 中该位置之后不足 6 字节（`VER TYPE LEN_L LEN_H SEQ FLAGS`），等待更多数据。
4. 解析 `VER`；`VER != 0x01` → 丢弃 MAGIC 首字节，回到 2。
5. 解析 `LEN`；`LEN > 2060` 或 `LEN` 与 TYPE 不自洽（见 4.1 / 4.3）→ 判定为非法长度，**丢弃 MAGIC 首字节**后回到 2（不能丢弃整个缓冲区，否则可能把后面紧跟的合法帧一起丢掉）。
6. 等待 `6 + LEN + 2` 字节齐备；到齐后计算 CRC（覆盖范围见第 5 节）并与帧尾比对。
   - 不匹配 → **丢弃 MAGIC 首字节**后回到 2（这样噪声/错帧之后的下一帧仍能被找回）。
   - 匹配 → 交给上层处理，并从缓冲区移除整帧，继续解析剩余字节（一次 read 可能含多帧 = 合并帧）。
7. **截断包恢复**：若某个已定位 MAGIC 的帧在 `FRAME_TIMEOUT = 1.0 s` 内仍未收齐，丢弃该 MAGIC 首字节并回到 2，同时在状态栏提示一次；不得无限等待。
8. 计数统计：有效帧、CRC 错误、非法长度、超时帧分别计数，供 UI 显示"数据状态"。

必须覆盖的测试情形：任意分片（含逐字节）、多帧合并、前置/中间噪声后重同步、CRC 错 1 位、长度字段被改大/改小、截断包后接一个合法帧能恢复。

## 7. 完整的十六进制样例（可直接作为跨实现核对的 golden vector）

以下三帧的 CRC 均由第 5 节算法独立计算，`crc16("123456789") == 0x29B1` 已核对。

### 样例 A：命令帧 SET_RATE = 100000 Hz，SEQ = 0x07

```
A5 5A C3 3C 01 20 05 00 07 00 04 A0 86 01 00 78 82
```
- payload = `04 A0 86 01 00`（cmd 0x04；100000 = 0x000186A0 → LE `A0 86 01 00`）
- CRC 覆盖 `01 20 05 00 07 00 04 A0 86 01 00` = **0x8278**（帧内 `78 82`）
- 连续字符串：`A55AC33C01200500070004A08601007882`

### 样例 B：采样帧，4 点，10000 Hz，vref = 3300 mV，SEQ = 0x2A

```
A5 5A C3 3C 01 10 12 00 2A 00 10 27 00 00 04 00 E4 0C 00 00 00 00 00 08 FF 0F D2 04 A4 7E
```
- payload 元信息：`10 27 00 00`（10000 Hz）、`04 00`（4 点）、`E4 0C`（3300 mV）、`00 00`（reserved）
- 4 个样本：`00 00` = 0、`00 08` = 2048、`FF 0F` = 4095、`D2 04` = 1234
- 换算电压：0.0000 V / 1.6504 V / 3.3000 V / 0.9944 V（按 `code/4095*3.3`，保留 4 位小数；其中 1234/4095×3.3 = 0.99443 V）
- CRC 覆盖 `01 10 12 00 2A 00 10 27 00 00 04 00 E4 0C 00 00 00 00 00 08 FF 0F D2 04` = **0x7EA4**（帧内 `A4 7E`）
- 连续字符串：`A55AC33C011012002A00102700000400E40C000000000008FF0FD204A47E`

### 样例 C：响应帧 ACK SET_RATE，SEQ 回显 0x07，status = OK

```
A5 5A C3 3C 01 21 0E 00 07 00 04 00 A0 86 01 00 E4 0C 00 00 00 00 00 00 3A E7
```
- payload = `04 00`（ack_cmd=0x04, status=0x00）、`A0 86 01 00`（实际 100000 Hz）、`E4 0C`（3300 mV）、`00`（IDLE）、`00`（flags）、`00 00 00 00`（frames_sent=0）
- CRC 覆盖 `01 21 0E 00 07 00 04 00 A0 86 01 00 E4 0C 00 00 00 00 00 00` = **0xE73A**（帧内 `3A E7`）
- 连续字符串：`A55AC33C01210E0007000400A0860100E40C0000000000003AE7`

## 8. 跨实现核对方法（避免"Python 自己编码自己解码"）

三方独立，不允许任何一方调用另一方的编码函数来生成自己的测试输入：

1. **固定 golden 字节串**：第 7 节的三帧以文本形式硬编码在 `docs/protocol.md`。电脑端测试**必须直接从本文读取/硬编码这些字节**，用自己实现的解析器解出全部字段与 CRC，逐一与本文给出的期望值比对。
2. **C 侧编译期断言**：固件把 `CRC_STEP` 宏同时用于运行时 `Protocol_Crc16` 和 `#if` 常量表达式断言（例如展开样例 A 的 11 个覆盖字节，断言结果 `== 0x8278`）。用 Keil ARMCC 实际编译该文件，**编译通过即证明 C 预处理器按协议算出的 CRC 与本文一致**；若不一致，`#error` 会让构建失败。这构成"C 编译器 ↔ Python/文档"的跨实现证据。
3. **C 侧 golden 帧常量**：固件测试文件中放一份与样例 B 逐字节相同的 `const uint8_t` 数组（人工按协议写成十六进制，不调用编码器），Python 侧解析该数组文本并核对。这样 Python 解析的是 C 侧的常量数据，而不是 Python 自己刚生成的包。
4. 三方结果（文档期望值 / Python 实现 / ARMCC 编译期断言）必须一致；任何一项失败都必须记为验证失败，不得用"改测试期望值"来通过。

> 说明：本机没有可在 PC 上执行的 x86 C 编译器，因此**不能**把固件 C 函数编译成 PC 可执行程序来跑；上述第 2 条是可在本机真实执行的跨实现核对。若后续有 GCC/MSVC，应补做"C 编码 → Python 解码"与"Python 编码 → C 解码"的双向运行级核对，此项在验证报告里列为待补。

## 9. 参数与状态语义小结（防止虚假显示）

| 情形 | 电脑端必须怎么做 |
| --- | --- |
| 采样率下拉框改变 | 发 SET_RATE，界面显示"切换中"；**只有**收到匹配 SEQ + status OK + `actual_rate_hz == 请求值` 才更新横轴与"采样率"标签；否则回滚并报错 |
| 参考电压改变 | 同上，必须回读 `vref_mv`；明确标注"仅设备本次运行有效，掉电不保存" |
| 未收到任何帧 | 显示"等待设备"，不能显示"测量中" |
| 模拟模式 | 界面显著标注"模拟数据"，硬件按钮禁用或明确提示，采样率来自模拟源配置而非真实设备 |
| 断线 | 状态栏显示"已断开"，冻结最后一帧但标注为历史数据，不能继续刷新假装在线 |
| 帧间空隙 | 时间轴每帧从 0 起，CSV 带 `frame_seq`；不得把多帧首尾相连画成连续采样 |
| 暂停 / 单次冻结 | 冻结后后台线程即使收到新帧也不得覆盖当前显示帧 |
